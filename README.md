# BrokerT

An independent, Tesla-focused investment and trading platform: a market terminal for a single
instrument, a working order lifecycle, a portfolio whose figures are derived rather than stored,
thematic investment strategies, a vehicle configurator, and a full administrative console.

> subject of the data shown.
>
> **BrokerT is not a regulated financial service.** It is not a registered broker-dealer, investment
> adviser, bank or money transmitter, and it is not licensed or insured. Nothing in it is investment
> advice or an offer to buy or sell any security.
>
> **Demo mode is on by default.** Prices, balances, orders, allocations and vehicle order requests
> are simulated. No order reaches an exchange, no payment rail is connected, and no real money moves.

## What is real and what is simulated

This distinction is the most important thing to understand about the project.

**Real.** Every user action writes to PostgreSQL and is enforced there. Registering creates an
account; placing an order runs a transactional database function that resolves the price
server-side, checks buying power under a row lock, and writes the order, the fill, the holding, the
wallet movement, the ledger entry and the notification together or not at all. Cancelling releases
reserved cash. Allocating to a strategy re-checks the minimum, maximum and remaining capacity
against the stored product. Administrative changes are audited. Nothing in the interface shows a
success message for an operation that did not happen.

**Simulated.** The prices those operations run against, and the balances they move, are generated by
the platform itself:

| Simulated | Where it comes from |
| --- | --- |
| Quotes and price history | `SimulatedMarketDataProvider` — a mean-reverting geometric random walk over a stored quote, plus five years of seeded daily candles |
| Cash balances | `demo_cash_movement()`, which refuses to run when demo mode is off |
| Order execution | The demo venue inside `place_order()` and `process_resting_orders()`; no order is routed anywhere |
| Strategy track records | A seeded, deterministic simulator (`src/lib/simulation.ts`) |
| Vehicle order requests | Records against the account; nothing reaches a manufacturer or dealer |

Every screen that shows one of these labels it as simulated. That labelling is a feature, not
boilerplate — do not remove it while demo mode is on.

## Architecture

```
Browser
  │
  ├─ Server Components ──────► services (src/lib/services) ──┐
  │                                                          │
  ├─ Server Actions ─────────► actions (src/lib/actions) ────┤
  │                              │                            │
  │                              └─► RPCs: place_order, cancel_order,
  │                                  create_investment_position,
  │                                  create_car_order, demo_cash_movement,
  │                                  admin_* …
  │                                                          │
  └─ Route handlers (quote, series, search, admin setup) ─────┤
                                                             ▼
                                              PostgreSQL (Supabase)
                                              • Row Level Security on every table
                                              • SECURITY DEFINER functions for
                                                every money-moving path
                                              • append-only audit log
```

Three rules shape the codebase:

1. **Authorisation lives in the database.** Every table is deny-by-default under RLS and scoped to
   `auth.uid()`. Route protection in `src/proxy.ts` and role checks in layouts are conveniences;
   they are not the security boundary.
2. **The client never dictates money.** Prices, balances and limits are resolved server-side inside
   a transaction. The order preview in the browser mirrors the database's arithmetic so the
   confirmation matches the outcome, but the database is the authority.
3. **Providers sit behind seams.** Market data, email and (in future) payments each have an
   interface with one implementation. Swapping one is a contained change.

**Stack:** Next.js 16 (App Router) · React 19 · TypeScript (strict) · Tailwind CSS v4 ·
Radix primitives · lightweight-charts · Recharts · Supabase (Postgres, Auth, RLS, Realtime) ·
Zod · Vitest.

## Getting started

```bash
git clone <your-fork> brokert && cd brokert
npm install
cp .env.example .env.local        # then fill in the Supabase values
npm run dev                       # http://localhost:3000
```

The app builds and renders without Supabase configured — every data-backed screen shows a setup
notice instead of throwing — but nothing works until you complete the Supabase setup below.

**Requirements:** Node.js 20.9+ (22 LTS recommended) and npm 10+.

## Environment variables

Copy `.env.example` to `.env.local`. Never commit real secrets.

| Variable | Required | Purpose |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | yes | Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | yes | Public anon key. Safe in the browser — RLS is what protects data |
| `SUPABASE_SERVICE_ROLE_KEY` | yes | **Bypasses RLS.** Server-only. Never prefix with `NEXT_PUBLIC_`, never import from a Client Component |
| `NEXT_PUBLIC_APP_URL` | yes | Canonical origin, used for auth redirects, emails and metadata |
| `NEXT_PUBLIC_DEMO_MODE` | no | `true` (default). Set to `false` only once real providers are connected |
| `MARKET_DATA_PROVIDER` | no | `simulated` (default) |
| `MARKET_DATA_API_KEY` | no | Credential for a licensed feed |
| `RESEND_API_KEY` | no | Without it, email is logged instead of sent |
| `EMAIL_FROM` | no | Sender identity |
| `ADMIN_EMAIL` | no | When set, only this address may be promoted by the bootstrap endpoint |
| `ADMIN_SETUP_SECRET` | no | Enables `POST /api/admin/setup`. Rotate or remove it once the first administrator exists |

The service-role key is used by exactly three things: the demo market engine (to persist a tick),
the admin bootstrap endpoint, and the CLI scripts. It is never reachable from the browser —
`src/lib/supabase/server.ts` carries `import "server-only"`, which makes a client import a build
error rather than a runtime leak.

## Supabase setup

1. Create a project at [supabase.com](https://supabase.com).
2. **Project Settings → API**: copy the URL, the `anon` key and the `service_role` key into
   `.env.local`.
3. **Authentication → URL Configuration**: set the Site URL to your `NEXT_PUBLIC_APP_URL` and add
   `<origin>/auth/callback` as a redirect URL.
4. **Authentication → Providers → Email**: leave "Confirm email" on. The app handles the
   unconfirmed-session case and tells the person to check their inbox.
5. Run the migrations (below).

## Database migrations

Apply the four files in `supabase/migrations/` **in order**. Either paste them into the SQL editor,
or use the Supabase CLI:

```bash
supabase link --project-ref <ref>
supabase db push
```

| File | Contents |
| --- | --- |
| `0001_schema.sql` | Enums, 25 tables, constraints, indexes, `updated_at` triggers, role helpers |
| `0002_functions.sql` | New-user provisioning and every transactional business function |
| `0003_rls.sql` | Row Level Security policies, guard triggers, realtime publication |
| `0004_seed_reference_data.sql` | Instrument, five years of simulated candles, six strategies, vehicle catalogue, platform settings |
| `0005_resting_orders.sql` | Settles resting limit and stop orders once the market reaches their price |
| `0006_guard_trusted_paths.sql` | Lets the service role through the column guards so the first admin can be created |
| `0007_grants.sql` | Explicit table privileges, so the schema does not depend on Supabase's defaults |

Or paste **`supabase/setup.sql`** — all of them concatenated in order, with a
verification block at the end — into the SQL editor in one go.

They are written to be safely re-runnable: enum creation is guarded, tables use
`create table if not exists`, policies are dropped before being recreated, and the candle generator
returns early if history already exists.

### Schema at a glance

`profiles` `user_settings` `wallets` · `assets` `market_quotes` `market_candles` ·
`portfolios` `portfolio_holdings` `portfolio_snapshots` · `orders` `order_fills` ·
`investments` `investment_positions` · `vehicles` `vehicle_options` `car_orders` ·
`transactions` · `watchlists` `watchlist_items` · `notifications` ·
`support_tickets` `support_messages` · `audit_logs` `login_events` `system_settings`

Money is `numeric`, never floating point. User-scoped tables denormalise `user_id` so every RLS
check is a single-column comparison.

## Row Level Security

RLS is enabled on **every** table, including reference data, and `force`d on the tables carrying
money and identity so even a table-owner connection is subject to it.

- A user reads only rows where `user_id = auth.uid()`. There is no policy that would let one account
  reach another's.
- `wallets`, `orders`, `order_fills` and `transactions` have **no** INSERT or UPDATE policy at all.
  Those rows are written exclusively by `SECURITY DEFINER` functions, so a compromised client token
  cannot mint a balance or a trade.
- `public.is_admin()` and `public.is_super_admin()` are `SECURITY DEFINER` helpers, so admin
  policies never recurse back into `profiles`.
- Guard triggers block privilege escalation (`role`, `account_status`, `kyc_status`), hide vehicle
  internal notes from customers, and restrict notification updates to the `read_at` column.
- `audit_logs` is admin-readable and rejects every UPDATE and DELETE via a trigger.

`tests/authorization.test.ts` asserts each of these guarantees is declared in the migrations, and
`tests/migrations.test.ts` catches SQL that would fail at runtime. Static checks only go so far, so:

```bash
npm run verify:db      # requires postgresql-16 server binaries
```

This starts a throwaway Postgres, applies a minimal stand-in for the parts of Supabase the
migrations touch, runs every migration, re-runs them to prove idempotency, and then exercises the
real thing: a market buy fills; a buy beyond available cash and an oversized sell are rejected; one
customer cannot see another's orders; a customer cannot change their own role; a direct wallet
write, a forged ledger row and a forged holding are all refused; the audit log is unreadable to a
non-admin; a resting limit order rests; a non-admin cannot call an admin function; and the service
role can still promote the first administrator.

## Seed data

`0004_seed_reference_data.sql` seeds only catalogue data — no accounts, no personal data.

For accounts with activity:

```bash
npm run seed:demo            # create fictional demo accounts
npm run seed:demo -- --reset # remove previously seeded accounts first
```

This creates six accounts on `@demo.brokert.example` — a non-deliverable domain, so a seeded address
can never reach a real inbox — each with a funded wallet, a filled order, a holding, a month of
portfolio snapshots and, for some, an allocation and a vehicle request. Everything is marked
`is_simulated`. The script prints the shared password. **Never run it against production.**

## Creating the first administrator

Roles are never set from the sign-up form. Register normally, then promote the account.

```bash
npm run setup:admin -- you@example.com
```

Or, with `ADMIN_SETUP_SECRET` set:

```bash
curl -X POST "$NEXT_PUBLIC_APP_URL/api/admin/setup" \
  -H 'content-type: application/json' \
  -d '{"email":"you@example.com","secret":"'"$ADMIN_SETUP_SECRET"'"}'
```

Both paths only elevate an **existing** account — neither creates one, and no password is ever put
in an environment variable or in source. The endpoint compares the secret in constant time, honours
`ADMIN_EMAIL` as an allowlist when set, and writes the promotion to the audit log. **Rotate or
remove `ADMIN_SETUP_SECRET` once the first administrator exists.** Thereafter, only a super
administrator can grant admin access, from the console.

Sign out and back in after promotion to pick up the new role.

## Demo mode

`NEXT_PUBLIC_DEMO_MODE` controls the interface; the `demo_mode` row in `system_settings` controls
the database. Both default to on.

Turning demo mode off does **not** make the platform live — it makes funding refuse to run, which is
the intended failure. Going live means connecting a licensed market-data feed, a regulated payment
provider and an identity-verification provider, and completing the compliance work each requires.

## Connecting a real market-data provider

`src/lib/market/types.ts` defines the seam:

```ts
export interface MarketDataProvider {
  readonly id: string;
  readonly isSimulated: boolean;
  getQuote(symbol: string): Promise<Quote | null>;
  getSeries(symbol: string, timeframe: Timeframe): Promise<MarketSeries | null>;
}
```

To connect Polygon, Finnhub, Twelve Data or another licensed feed:

1. Implement the interface in `src/lib/market/`.
2. Register it in the switch in `src/lib/market/provider.ts`.
3. Set `MARKET_DATA_PROVIDER` and `MARKET_DATA_API_KEY`.

Return `isSimulated: false` on the quote and the simulation labelling disappears from the interface
on its own. Nothing in the UI, the portfolio valuation or the order engine changes — they all read
through the interface.

## Email

`src/lib/email/` wraps the provider. With `RESEND_API_KEY` set, messages go through Resend; without
it they are logged to the server console, so local development and CI never depend on an outbound
mail provider and never send to a real inbox by accident. Delivery failures are caught and never
fail the transaction that triggered them.

Templates cover welcome, order confirmation, security alert, allocation confirmation and vehicle
order request. Every template carries the demo-mode banner while demo mode is on.

## Deploying to Vercel

1. Import the repository.
2. Add every variable from [Environment variables](#environment-variables) to the project. Set
   `NEXT_PUBLIC_APP_URL` to the deployment origin.
3. Add that origin to Supabase → Authentication → URL Configuration.
4. Deploy. Build and start commands are the defaults.

The app is Vercel-compatible with no adapter: Server Components and Server Actions for the product
surface, route handlers for the polled quote endpoint and the search endpoint, and `src/proxy.ts`
for session refresh.

## Production checklist

Do not put this in front of real customers without working through all of it.

**Legal and regulatory**
- [ ] Take advice on licensing in every market you intend to serve. Operating a real brokerage or
      handling client money is a regulated activity almost everywhere.
- [ ] Have a qualified lawyer review the terms, privacy policy and risk disclosure. The versions
      shipped here are templates and are not legal advice.
- [ ] Set the governing law and dispute-resolution provisions to match where you actually operate.
- [ ] Confirm the trademark position on every nominative reference.
- [ ] Complete the AML/KYC programme before enabling any funding.

**Providers**
- [ ] Connect a licensed market-data feed and honour its redistribution terms.
- [ ] Connect a regulated payment provider; remove or disable `demo_cash_movement()`.
- [ ] Connect an identity-verification provider and wire it to `kyc_status`.
- [ ] Connect a real execution venue or broker, or remove the trading surface entirely.

**Security**
- [ ] Enable TOTP enrolment and require it for every administrative role.
- [ ] Run `npm run verify:db` in CI so a weakened policy fails the build.
- [ ] Put rate limiting in front of the auth routes and the search and quote endpoints.
- [ ] Rotate `ADMIN_SETUP_SECRET` and confirm `/api/admin/setup` returns 404.
- [ ] Confirm the service-role key is absent from every client bundle.
- [ ] Add security headers (CSP, HSTS, frame-ancestors) and review cookie flags.
- [ ] Set up error tracking and alerting.

**Data**
- [ ] Enable point-in-time recovery and test a restore.
- [ ] Schedule the daily `portfolio_snapshots` job that the performance chart reads.
- [ ] Define retention for `login_events` and `audit_logs`.
- [ ] Run `npm run seed:demo -- --reset` and confirm no demo account survives.

**Quality**
- [ ] Add end-to-end coverage for register → fund → trade → allocate.
- [ ] Add integration tests that run the RLS policies against Postgres.
- [ ] Audit with a screen reader and at 200% zoom.
- [ ] Check every screen at 320px and confirm nothing scrolls horizontally.
